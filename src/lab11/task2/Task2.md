# Завдання 2. Контракти DoR / DoD та правила переходів Workflow

## Контекст

Контракти призначені для системи продажу квитків кінотеатру «Кадр». Вони є підготовленим вмістом для BRD, розділ 7.2. Кожен критерій має бінарний доказ; статус задачі не може бути змінений лише на підставі усної домовленості.

## Таблиця 7.2.1. Definition of Ready (DoR)

Усі критерії мають бути «Так» перед переходом `Backlog → To Do`.

| ID | Бінарний критерій | Доказ для перевірки |
|---|---|---|
| R1 | User Story має формат `As a … I want … so that …` і прив'язана до затвердженого Epic у Jira. | Посилання на Epic та опис задачі в Jira. |
| R2 | Заповнено щонайменше 3 Given–When–Then сценарії: основний сценарій, граничний випадок і відмова/помилка. | Acceptance Criteria у Jira; сценарії мають однозначні вхідні дані та очікуваний результат. |
| R3 | Для серверної або інтеграційної зміни визначені зачеплені класи/компоненти, endpoint та JSON-поля; контракт узгоджений зі схемою даних. | Посилання на UML/SRS/API-контракт; якщо зміни немає, задача явно позначена як UI-only або документаційна. |
| R4 | Зовнішні залежності або закриті, або мають власника й дату; для недоступного зовнішнього API визначено узгоджений mock. | Запис у Decision Log, посилання на специфікацію або mock endpoint та призначений власник блокера. |
| R5 | Оцінка задачі числова і записана: Story Points для Story або години для технічної задачі. | Поле Estimate в Jira заповнене після refinement. |
| R6 | Задача має Component із переліку Backend, Frontend, Infrastructure, QA та один Priority із Blocker, Critical, Major, Minor. | Поля Component і Priority в Jira; за потреби дозволено кілька компонентів, але один має бути основним. |
| R7 | Для резервування/продажу місця визначений очікуваний результат при повторному запиті або одночасній спробі купити останнє місце. | Acceptance Criteria та посилання на відповідний тестовий сценарій. |

**Відхилення:** якщо бодай один пункт має відповідь «Ні», задача залишається в `Backlog`; відсутність критерію не вважається його виконанням.

## Таблиця 7.2.2. Definition of Done (DoD)

Всі застосовні умови мають бути виконані перед переходом `Testing / QA → Done`.

| ID | Середовище | Бінарна умова / поріг | Доказ |
|---|---|---|---|
| D1 | Local Dev | Форматтер і лінтер завершуються з 0 помилок; unit-тести зелені; покриття нової/зміненої бізнес-логіки не менше 80%. | Звіт локального запуску або CI job із метрикою покриття. |
| D2 | Local Dev → Git | Pull Request має щонайменше 1 approve від іншого інженера; усі зауваження вирішені; секрети та ключі не додані до репозиторію. | Статус PR, результати secret scan та checklist review. |
| D3 | Staging / CI | CI build та всі інтеграційні/контрактні тести завершились успішно; міграції БД застосовуються на чистій тестовій БД і мають перевірений rollback або задокументований forward-fix. | Зелені CI jobs і лог тестового застосування міграцій. |
| D4 | Staging / QA | QA пройшов Acceptance Criteria; автоматизовані регресійні тести зелені; відкритих Blocker/Critical дефектів — 0. Для одночасного продажу останнього місця тест підтверджує не більше одного успішного продажу. | Test run, defect query з нульовим результатом та звіт concurrency-тесту, якщо зміна зачіпає місця/продаж. |
| D5 | UAT | PO/BA прийняв фічу на UAT за Gherkin-сценаріями; усі обов'язкові бізнес-сценарії мають результат Pass. | Підписаний/зафіксований UAT checklist із посиланням на задачу. |
| D6 | Production | Задеплоєно узгоджену версію; health check проходить; наявний dashboard/log alert для нової критичної операції; rollback-процедура визначена. | Deployment record, health check і посилання на моніторинг/rollback runbook. |
| D7 | Production / документація | Оновлено API/SRS або схему даних, якщо контракт змінився; Release Notes містять версію та зміни; документація доступна команді підтримки. | Посилання на оновлену документацію та Release Notes. |

## Таблиця 7.2.3. Матриця правил переходів статусів

Workflow складається із семи статусів: `Backlog`, `To Do`, `In Progress`, `Code Review`, `Testing / QA`, `Blocked`, `Done`.

| Поточний статус | Цільовий статус | Хто ініціює | Обов'язкова умова (Quality Gate / Guard) | Заборонені переходи / причина |
|---|---|---|---|---|
| Backlog | To Do | Product Owner / BA або Scrum Master | Усі DoR R1–R7 мають статус «Так»; є Epic, Component, Priority та Estimate. | Заборонено, якщо хоча б один DoR критерій не виконаний. |
| To Do | In Progress | Розробник, який бере задачу | Виконавець призначений; WIP-ліміт In Progress не перевищений; задача відповідає DoR. | To Do → Done / QA заборонено: немає реалізації та перевірки. |
| In Progress | Code Review | Автор PR | PR прив'язаний до задачі; build/unit tests зелені; зміни описані; автор не є єдиним reviewer. | In Progress → Testing / QA або Done заборонено: обхід peer review. |
| Code Review | Testing / QA | Reviewer / Tech Lead | Мінімум один approve; усі коментарі закриті; CI та contract tests зелені; PR змерджено у цільову гілку. | Code Review → Done заборонено: немає перевірки на Staging/UAT. |
| Code Review | In Progress | Reviewer / Tech Lead | Є хоча б одне невирішене blocking зауваження; воно описане в PR. | Перехід без конкретного зауваження заборонений; задачу не повертають до To Do. |
| Testing / QA | In Progress | QA Engineer | Виявлено дефект; заведено/зв'язано defect із кроками відтворення та очікуваним/фактичним результатом. | Testing / QA → Code Review / To Do заборонено: виправлення потребує нового циклу розробки. |
| Testing / QA | Done | QA Engineer (за зелених бізнес-gates) | Усі D1–D7 застосовні умови виконані; Blocker/Critical дефектів — 0; UAT прийнятий PO/BA; QA додає test evidence. | Testing / QA → Done заборонено без доказів будь-якої застосовної умови DoD або з відкритим Blocker/Critical. |
| To Do, In Progress, Code Review, Testing / QA | Blocked | Будь-який член команди; власник задачі фіксує блокер | Заповнені причина, зовнішня залежність/дефект, відповідальний і дата наступного перегляду; зберігається `previousStatus`. | Заборонено ставити Blocked без пояснення та власника; Backlog і Done не є активними статусами для цього переходу. |
| Blocked | Попередній активний статус | Власник задачі після підтвердження усунення блокера | Причина блокування закрита; додано доказ. Якщо блокер вимагав змін коду — повернення лише в In Progress; інакше — у збережений `previousStatus`. | Заборонено перейти одразу в Done; після зміни коду не можна повертатися безпосередньо в Code Review або QA. |

### WIP-ліміти для конфігурації дошки

| Колонка | Максимум карток | Дія при досягненні ліміту |
|---|---:|---|
| In Progress | 3 | Не брати нову задачу; допомогти завершити вже розпочату. |
| Code Review | 2 | Команда спершу виконує рев'ю черги, нову роботу не починає. |
| Testing / QA | 2 | Зменшити вхідний потік і допомогти усунути блокери тестування. |

`Blocked` відображається окремо і не використовується для обходу WIP-лімітів: задача зберігає WIP-слот колонки, з якої була заблокована, доки не повернеться або не буде завершена. Власник борда контролює це правило під час огляду блокерів.

## ШІ-аудит і прийняті виправлення

Це зафіксований навчальний аудит контрактів; зовнішню сесію LLM або Jira/Confluence у репозиторії не запускали.

| ID | Зона | Критична перевірка | Прийняте виправлення |
|---|---|---|---|
| QG-01 | DoD / Staging | Перевірка лише «тести зелені» не гарантувала відсутність подвійного продажу одного місця. | Додано вимірний concurrency-тест: одночасні спроби продати останнє місце мають завершитися максимум одним успішним продажем. |
| QG-02 | Workflow | Не було визначено повернення із Blocked; задача могла зависнути або перейти прямо в Done. | Додано збереження `previousStatus`, умову закриття блокера і заборону прямого переходу в Done; після зміни коду задача повертається в In Progress. |
| QG-03 | DoD / DB | Не було доказу, що схема БД оновлюється безпечно. | У D3 додано перевірку міграції на чистій тестовій БД і rollback або документований forward-fix. |
| QG-04 | Workflow / авторизація | Виконавець міг би самостійно підтвердити завершення без незалежних доказів. | Done дозволено ініціювати QA Engineer лише після виконання DoD, тестових доказів і бізнес-приймання PO/BA. |

### Decision Log

| ID | Рішення | Причина | Перевірка |
|---|---|---|---|
| D1 | Міграції перевіряються на чистій тестовій БД до виходу з Staging/CI. | Запобігання несумісній схемі та помилкам під час розгортання. | CI зберігає лог застосування міграції та її rollback/forward-fix. |
| D2 | Blocked зберігає попередній активний статус; при зміні коду вихід тільки в In Progress. | Усунення глухого кута й обходу Code Review/QA після блокування. | Перехід із Blocked у Done або до QA після зміни коду відхиляється workflow guard. |
| D3 | DoD включає concurrency-тест резервування місця та незалежний QA evidence перед Done. | Захист від подвійного продажу та самоприймання задачі автором. | Test report підтверджує не більше одного успішного продажу; є QA test run і UAT result. |

## Перенесення в Jira / Confluence

- Таблиці DoR, DoD і Workflow Rules призначені для BRD, підрозділ 7.2.
- Таблиця переходів є специфікацією для Jira Workflow; сама документація не змінює конфігурацію Jira.
- Дошка, Components, Priorities, WIP-ліміти та скриншот для Demo Day мають бути налаштовані й додані в робочому Jira/Notion окремо.
